Case study · Agents & MCP

Workflow vs. agent isn't a vibe — it's who owns the control flow. Here's proof, not just a diagram.

A plain-language breakdown of two architectures, why my own pipeline is deliberately one and not the other, and a live MCP connector doing three things a plain chat window can't.

Workflow vs. agent, in my own words

Workflow

I (or the developer) decide the steps ahead of time, and the LLM fills in each step. The code path is fixed — step 1 always leads to step 2, then step 3 — even though the LLM does the actual thinking inside each step. The control flow belongs to the code, not the model.

Agent

The LLM decides what to do next, based on what it sees in the environment. Nobody wrote "call tool A, then B, then stop" in advance — the model looks at each result and decides the next action, in a loop, until it thinks it's done or hits a limit. The control flow belongs to the model.

The cleanest test I've found: in a workflow, swap the LLM for a dumber version and the shape of execution doesn't change — same steps, same order, just lower quality at each one. In an agent, a dumber model might take a completely different path through the same tools, because the path was never fixed.

Classifying my own pipeline

My weekly-brief pipeline is a workflow — specifically prompt chaining. I decided there would be exactly five steps, in that order, before running it even once. The LLM never chose to skip a step or reorder anything; it filled in content, but I owned the path. That was the right call: the task is well-defined and repeatable, so a fixed path with inspectable checkpoints was worth more than letting a model improvise research on its own.

What MCP actually solves

MCP (Model Context Protocol) is a standard way to connect a model to things outside its own head — files, live data, other services — without every AI application needing a custom one-off integration for every tool. Anthropic's framing fits: a single standard connector instead of a different plug for every device, the way USB-C replaced a drawer of proprietary cables.

Before MCP, connecting Claude to Google Drive and arXiv and a database meant building three separate custom integrations that wouldn't transfer to any other AI application. With MCP, a server built once for one service plugs into any MCP-compatible client.

Three primitives — who decides when it gets used

Tools Actions the model calls on its own — it decides, mid-conversation, "I need this." Below, the model chose to call three tools in sequence, based on what each returned.
Resources Read-only data the application hands the model, not something the model reaches for itself — data placed in front of the model, not an action it takes.
Prompts Reusable, user-triggered templates — a person picks "run the weekly report" and the server executes a predetermined set of steps.

Evidence: three real tool calls, not a diagram

I connected the alphaXiv MCP server and ran three real calls — each one something plain chat alone cannot do:

1 · discover_papers

Searched arXiv live for recent (2026) papers on hybrid retrieval and reranking. Returned a ranked list of actual, dated papers, including one published the day before this conversation (2026-08-04) — not something available from training data alone.

2 · answer_pdf_queries

Pulled specific, cited content out of the full PDF of a hybrid retrieval and reranking paper (arXiv 2605.01664) — exact methodology, plus a citation-grounding result of 100% claim-level grounding accuracy on its 25-query pilot. Plain chat has no access to a PDF's full text or precise figures — only whatever summary happened to be in training data, if anything.

3 · read_files_from_github_repository

Read the actual source and README of a live GitHub repository — facebookresearch/DPR (Dense Passage Retrieval, the foundational hybrid-retrieval paper cited across several other searches this session) — with live file sizes and full contents pulled at request time, not recalled from memory.

What this pipeline would need to become an agent

Right now the weekly-brief workflow is fixed: five steps, always the same order, one topic per run. To make it an actual agent, the biggest change would be handing the model the decision of what to research and how deep to go, instead of me handing it a topic and a five-step script.

Concretely: instead of picking five topics and running the same five steps on each, I'd give the model a goal — "build a comprehensive AI/ML weekly brief" — plus a toolset (web search, the alphaXiv connector, maybe last week's brief as memory) and let it decide how many topics matter, which deserve a deep dive versus a mention, and when it's gathered enough to stop and write.

The tradeoff is real: an agent here costs more (tokens, tool calls, unpredictable runtime) and is harder to audit — I can't diff this week's five fixed steps against last week's. For a task this small and repeatable, that tradeoff isn't worth it yet. But it's the concrete next step if the workflow ever needs to handle "figure out what's worth covering," not just "cover what I already picked."
